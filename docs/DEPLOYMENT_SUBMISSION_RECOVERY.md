# 部署提交恢复

控制台在发送部署请求前，将原 `requestKey` 和配置 SHA-256 摘要写入当前浏览器会话的 `sessionStorage`。索引按 `/me` 的 subject 和 Agent ID 分隔，不保存提示词、环境变量或完整配置。写入及读回校验失败时不发送。

网络断线、502/504 和其他失败响应均保留原编号。刷新、切页签或离开详情再返回可恢复核对入口；账户或 Agent 切换清空页面内配置，并隔离迟到响应。提交期间阻止重复点击，异步计算摘要后再次核对当前身份和索引。

`GET /api/agents/{agentId}/substrate/deployments/requests/{requestKey}` 只查询数据库中的原部署，返回编号、Agent、部署标识、版本、状态和首实例标识。查询不解析配置、不联系运行时、不启动或恢复部署，且不受最近20条列表限制，也不因 Agent 后续退役或运行时停用而拒绝已有记录。权限与发布能力一致，统一来自 `PlatformPermission.DEPLOY_AGENTS`。部署仍是现有平台协作资源；查询不是新增的逐用户私有部署 ACL，前端 subject 隔离用于隔离本地待确认意图。

`NOT_FOUND` 仅表示查询时尚无已提交记录，不能证明原 POST 永远不会提交。页面保留编号，允许继续查询，或重新填写原配置后按原编号提交；摘要不一致则阻止发送。后端原有 `(agent_id, submission_key)` 唯一约束和冻结配置比较负责最终去重。并发竞争中的一方可能收到错误，随后应查询原键，不能改用新键。

获得匹配的已受理回执后才清除待确认索引；后续执行状态在部署版本中查看。失败版本仍通过原有“从失败步骤重试”操作继续，不自动新建版本或首实例。

边界：

- 没有自动重发、轮询受理查询或清除未知编号；查询未找到时不会自动换键。
- 关闭浏览器会话、清除存储、换设备后不保证自动恢复。编号和摘要不是跨标签页共享的全局意图锁。
- 刷新不恢复原配置正文；按原编号再提交须重新填写相同配置。无法恢复原配置时继续查询或人工核对，不自动生成新编号。
- 客户端摘要是本地防误操作约束，服务端原键及冻结配置才是数据一致性边界；故意换键创建新意图不在本次保证内。
- 需要浏览器安全上下文中的 Web Crypto；不可用时停止发送并提示。现有本机 `localhost` 入口支持该能力。
- 不改变部署工作线程、实例身份协议、Runner、数据库迁移或历史未知预算，不进行真实模型调用。
