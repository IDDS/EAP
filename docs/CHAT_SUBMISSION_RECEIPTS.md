# 聊天提交与原回执

EAP 控制台聊天先在数据库登记提交身份，再唤醒实例和派发。重复 POST 不会再次派发；GET 只读取原回执，不唤醒实例、不续期、不预留预算。

## 接口与身份

- `POST /api/agents/{agentId}/substrate/instances/{name}/chat` 必须包含小写 UUID `requestKey`、`message` 和可选 `history`。旧客户端缺少编号时返回 400，不能让服务端代造新编号。
- `GET /api/agents/{agentId}/substrate/instances/{name}/chat/{requestKey}` 查询原回执。
- 两个接口都使用 `PlatformPermission.OPERATE_INSTANCES`，前端遵循 `/me` 的 `operateInstances`。回执另绑定原认证 subject：其他 operator/admin 也不能读取他人的回执。
- V85 的主键为 subject 的 SHA-256 与 requestKey。冻结摘要包含 Agent、实例名称、消息及完整显式历史。相同编号改消息/历史返回 409；换 Agent/实例也拒绝。重复请求不会新建观测或恢复执行。
- 回执不依赖当前实例仍存在；键不会自动过期删除，避免迟到重放再次派发。

## 状态与故障边界

| 状态 | 含义与后续动作 |
|---|---|
| `ACCEPTED` | 已持久登记，正在做前检；只能查询原编号。 |
| `DISPATCHED` | 派发屏障已提交，可能已发送到 Runner；只能查询。 |
| `SUCCEEDED` | EAP 已持久确认完整成功回执。首次响应携带正文，重放/查询仅返回完成元数据。 |
| `NOT_DISPATCHED` | 本次处理明确在派发屏障前失败，原编号保持终态；用户可开始新请求。 |
| `UNKNOWN` | 派发后发生异常，或超过五分钟仍未确认；禁止按原编号重新派发。 |

只有成功插入回执的原处理器能进入派发。外部调用在事务外，派发前通过条件 UPDATE 提交 `DISPATCHED`；期限已过则不能发送。成功状态必须先提交，再向浏览器返回正文。

查询超期 `ACCEPTED` 也保守返回 `UNKNOWN`，因为纯读取不能证明另一事务不会提交。查询不改写数据库状态，迟到的合法成功回执仍可确认。不存在的编号不会被当作“确定未调用”：迟到 POST 仍可能到达，前端保留编号继续核对。

此机制保证 EAP 原提交不自动重复派发，不承诺外部供应商的 exactly-once。Runner 或后端在派发后丢失结果可能永久 UNKNOWN；本轮没有增加供应商回执协议、UNKNOWN 人工结算或正文恢复。已准入调用仍可能计费，预算未知占用规则保持。

## 正文与前端恢复

数据库仅存身份摘要、载荷/结果摘要、状态、时间、轮数及规范化 Trace ID，不存消息、历史、答案或异常原文。回执查询不会绕过已有观测正文权限与保留策略。

浏览器在发送前把编号写入按 subject/Agent/实例分隔的 `sessionStorage`；验证写入成功后才 POST。刷新、切页、切实例和迟到响应都不会删除未确认编号。待确认期间禁用发送/新对话，提供“查询原回执”和原 Trace 链路。明确成功/未派发后才移除编号。

完整问答只在当前窗口内存保留，并且只追加首次成功响应一次。查询确认成功但没有正文时清空上下文，避免把不完整问答用于下一轮。浏览器会话存储不包含聊天正文；关闭浏览器会话、主动清理存储或换设备不保证自动找回编号，服务端原回执仍保留，可凭原编号查询。不同标签页不是共享会话，本轮没有跨标签页锁或服务器聊天列表。
