# 个人记忆候选：范围、治理与验证

状态：本功能是未部署的候选实现。它让有权限的用户手工保存、查看和撤回自己的记忆；**尚不自动从对话提取内容，也不向智能体或模型提供记忆**。代码和界面不能作为企业级长期记忆服务已经验收的证据。

## 用户可以做什么

- 在“我的记忆”中明确填写内容并保存，可选填写过期时间。没有自动摘要、自动写入或模型调用。
- 按保存时间倒序查看自己的记录，列表分页读取；到期记录仍显示为“已过期”，以便用户主动撤回。
- 撤回时清空当前数据库记录中的正文，同时保留不含正文的操作审计与防重复标识。已存在的备份、数据库日志或其他副本不在此操作范围内，不能承诺物理彻底擦除。
- 到期目前只改变列表状态，不会自动清除数据库内容；目前没有模型召回路径，未来接入时必须另行验证到期和撤回后的可见性。

## 身份和数据边界

- 接口使用认证 JWT 的 issuer 与 subject 共同派生归属；不能由请求指定其他人的身份。`OPERATOR`、`PLATFORM_ADMIN` 通过集中式 `manageOwnMemory` 能力访问自己的记录。平台管理员通过这些接口也不能查看或撤回其他主体的记录。数据库及备份的管理权限不由此接口控制。
- 开发免登录模式不提供个人记忆访问：即使通用开发配置放行请求，也必须有受认证的 JWT 主体。主体、发行方缺失时拒绝访问。
- 用户输入为不可信业务内容。当前不自动检查或屏蔽密码、令牌、个人信息等敏感内容；页面提示不要填写密码或令牌。投入真实业务前，须由企业确定允许范围、分类、安全检测及存储控制。
- 记忆正文存入应用数据库，创建和撤回的审计仅含派生主体标识、操作和记录编号，不保存正文。没有做独立加密、自动到期擦除、备份清除或审计保留期验证。
- 候选按当前平台信任域和数据库部署；同库多租户隔离、组织或团队共享、身份迁移及外部模型的数据边界均未实现或验证。

## 请求和异常处理

`GET /api/personal-memories` 按当前主体分页读取；游标仅表示排序位置，不赋予访问权。`POST /api/personal-memories` 要求用户明确确认，并携带客户端生成的提交编号；相同主体、相同编号与相同内容的重复请求返回原记录，同编号的不同内容被拒绝。`POST /api/personal-memories/{id}/revoke` 仅允许原主体撤回，重复撤回不会恢复正文。

网络超时不证明写入未发生，应使用原编号重试或刷新原列表核对。页面仅在当前会话保存待确认的提交编号与内容，页面刷新后不会持久保存待提交草稿。创建和撤回是数据库事务，但无法撤销请求已经返回给调用方的内容或清除先前备份。

## 验证与发布条件

已收集的证据和待执行任务以[项目记忆](PROJECT_MEMORY.md)末尾记录为准；此前独立 MySQL 8.4 的 5 项用例通过，新增的并发、跨主体同编号以及 V98→V99 升级测试尚未完成。测试使用模拟 JWT、合成内容和隔离数据库，不代表真实身份提供方或客户环境已验收。

发布前至少要完成：

1. 在远程隔离环境运行当前源码的 H2 与 MySQL 测试，覆盖两个主体、并发重试、撤回和升级；确认临时资源已清理。
2. 在远程浏览器使用模拟接口验证桌面和手机的保存、撤回、权限变化及不可信内容显示；再另行验证真实身份登录与会话切换。
3. 明确数据库及备份访问、保留、恢复和清除责任，制定 V98/V99 的升级、混合版本及回滚方案。
4. 如需向智能体提供记忆，先设计明确授权、用途和作用域、来源、冲突、过期和撤回后召回规则，再以两个主体和跨会话测试验证；当前实现没有该能力。
