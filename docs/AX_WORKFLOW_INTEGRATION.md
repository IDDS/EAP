# EAP / AX / Substrate 串行统一编排

本轮将独立 AX 任务接入已有工作流引擎与 Team/Plan，并统一基础设施监控入口和执行时间线。保留原生 Runtime 路径；两种后端可以在同一串行计划中交替使用。

## 使用方式

- 工作流：选择 AGENT/ARTIFACT 节点，在“执行后端”选择 AX 并保存。默认模型任务；配置 JSON 可设置 axMode=ECHO/FAIL 做明确的合成验收。inputFrom 引用已执行前序任务的真实 output。
- 团队计划：新增步骤时选择原生 Runtime 或 AX，分配团队成员后执行。后端选择随计划一起冻结；AX 步骤固定使用 LLM 模式。
- 时间线：AX 步骤显示实际 AX taskKey 和 ax:// 沙箱标识，点击链接打开关联任务；AX 详情显示工作流、运行及节点来源。详情深链通过单任务 API 查询，不受最近 100 条列表限制。
- 监控：在 Substrate 运行监控切换“原生 Runtime 池”/“AX 任务池”。固定 PromQL 分别查询 eap-agents/eap-ax，缓存按池和时间窗口隔离。AX 池展示最近任务的业务状态、沙箱状态及工作流归属，可继续下钻。

## 执行与一致性

V51 为计划步骤增加 execution_backend（历史记录默认 RUNTIME），为 ax_tasks 增加 workflow_id、workflow_run_key、workflow_node_key。AX 工作流提交使用独立的幂等命名空间，保留既有独立任务的幂等键算法。

提交前校验选定路径、执行后端、AX 可用性及 Agent ACTIVE 状态；计划生成、冻结和入队维持同一事务。AX 实际任务在执行至该节点时创建，提交前再次校验 Agent。目标与上下文（含前一步真实结果）合并发送给原有 AX Runner，上限 8000 字符且不超过 24KB；超过上限时阻止该节点派发。

AX Worker 与工作流线程独立协调。工作流只等待 AX 持久化业务回执，不把沙箱 Ready/Running 视为成功。业务成功后还须确认物理休眠，才进入后续节点；AX 沙箱为每任务独立创建，始终自动休眠。原生 Runtime 的休眠仍由 suspendAfterTask 显式控制。

原始输出仅通过 VIEW_CONTENT 接口提供，普通时间线与监控任务列表只返回元数据。前端关闭详情、切换对象或身份时清除内容，并丢弃失效响应。

## 边界

- 仍为串行编排，分支依赖提交上下文；未实现并行、动态结果分支或自动选 Agent。
- 沿用原工作流总期限（PoC 900 秒）。AX 节点期限绑定同一总期限；异步 AX 回执不等于整个工作流获得无限时长或重启续跑能力。
- 工作流进程失联、超时或 AX 结果未知时保留原任务，停止下游，不自动重派。独立 AX 核对可能接收迟到回执，但不会自动续跑已终止的工作流。
- AX 业务成功但休眠未确认时继续等待至总期限；已保存输出不会丢失，不因此重跑业务。
- 没有新增生产身份、每任务凭证隔离、TLS、灾备、规模保证、取消/补偿、Git/MCP/Skills 工作区支持。AX 当前仍使用固定模型与自定义 Runner。
- 原生与 AX 指标按池分别展示，不伪装成单实例资源指标；日志检索、基础设施 Trace 自动关联和自动告警仍未实现。
