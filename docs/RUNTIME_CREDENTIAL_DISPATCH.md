# 派发前的短期凭证读取

自动配送在独立事务中确认新的短期凭证。实验配置读取和实验提交先在各自事务中检查准入，因此可能已经把旧的 `RuntimeConnection` 放入 JPA 一级缓存。配送成功后再次查询同一实体，调用方仍可能得到旧对象：旧租约已过期时被拒绝；尚未到期时则返回与实例当前安装值不同的凭证。

`RuntimeConnectionService.dispatchToken` 使用 `Propagation.NOT_SUPPORTED` 暂停调用方事务。配送和后续读取不再沿用调用方的持久化上下文或数据库快照，派发使用配送确认后的值；返回后原调用方事务继续。不要用全局 `EntityManager.clear()` 清除其他业务实体，也不要通过延长租约或重派模型掩盖此问题。

该方法仍检查纳管记录、配置可用性、租约及验证状态，并核对原生 UID 和模板。自动配送继续使用原身份批准与期限，撤销和过期批准仍阻断。该改动不签发新身份、不延长批准、不变更预算或工具权限、不增加模型重试。

回归覆盖调用方只读/写事务与租约已过期/临近到期四种组合：先读准入，再派发，确认派发值与实例安装值相同、旧值失效、身份周期和批准期限保持、序号仅增加一次。远程旧实现四项均失败，修复后定向 103 项/6 类、完整 617 项/94 类及打包通过，零失败、错误、跳过。

实际 MySQL68、后端健康与 Pod 镜像摘要通过。原 UID `20e48478-5c79-4c66-8cda-99783235b26b` 的租约自然过期后，配置读取 200、旧客体凭证 401、新客体凭证 200，序号 3→4，身份 epoch 与批准期限保持，模型调用始终为原 56 次。凭证只用于节点进程内存中的验证，没有写入证据。发布前后 25 表原行、费用、认证和其他镜像保持。

T3-E 独立对照第二批首次准入 HTTP 400 没有生成实验或额外预占。仅在修复、当前配置和原费用核对通过后，允许恢复一次完全相同提交键和参数的原准入，并持久保留首 400、参数摘要及恢复标记。未知提交只查询原键；已经持久化的 FAILED/UNKNOWN 实验不重放。原 C 的瞬时 `RUNTIME_NOT_READY` 原因仍未确认，该修复不能倒推其根因或改写其结果。
