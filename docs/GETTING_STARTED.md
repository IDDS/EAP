# 从控制台到一次多智能体执行

EAP 的首次安装分为两个阶段：先建立可登录、可持久化的控制平面，再接入运行系统。前后端健康检查通过，只证明控制台服务可用。

## 1. 准备试点环境

在远程开发服务器或 Kubernetes 集群执行构建、测试与部署。先准备：

| 依赖 | 最低接入要求 |
| --- | --- |
| 数据库 | 独立 MySQL 8 数据库、迁移权限、持久存储与恢复方案 |
| 企业身份 | OIDC Authorization Code + PKCE S256 公共客户端、issuer、audience、角色 Claim |
| 控制台入口 | 浏览器可访问的 origin、回调地址 `/auth/callback`；正式入口配置 HTTPS |
| 运行系统 | 与当前 EAP 适配兼容的 Substrate、可用运行池及受控镜像仓库 |
| 模型服务 | 在网关侧配置 OpenAI 兼容上游；模型名称、输出上限与账户权限由实际供应商确认 |
| 凭据管理 | Secret 或外部凭据系统；配置文件仅保存引用，不保存秘密值 |

新环境从[安装配置示例](../deploy/delivery/install/config.example.json)建立自己的配置和发布清单。镜像引用须是目标环境已准备、核验的固定摘要。仓库里的既有环境发布清单不是公共镜像下载服务。

## 2. 安装控制平面

按[JWT 首次安装说明](../deploy/delivery/install/README.md)执行：

1. `bootstrap.py render`：生成固定配置的安装包，并独立记录摘要。
2. `bootstrap.py preflight`：核对命名空间、引用、对象冲突与服务端 dry-run。
3. `bootstrap.py install`：检查独立数据库为空，再创建控制台资源；保存原安装回执。
4. `bootstrap.py status`：查询原资源状态。

工具不会安装 MySQL、IdP、Substrate、Ingress 或 TLS，也不会自动恢复部分失败的安装。超时后先查原资源与回执，避免重复安装。

用目标 IdP 的真实账号登录，分别验证：

- `/api/platform/me` 返回 `JWT` 模式与预期能力。
- 无令牌的受保护 API 返回 401；无能力的操作返回 403。
- 浏览器按钮与 `/me` 能力一致，退出后受保护内容清除。
- 页面刷新、窄屏布局、后端健康及数据库持久化符合要求。

没有仓库通用默认账号。IdP 管理员创建主体并分配角色。权限规则集中在后端 `PlatformPermission`，前端不依据角色名称自行推导权限。

## 3. 接入执行平面

为该环境配置 Substrate 路由、工作空间、运行镜像、模型网关、实例身份配送和预算。模型上游凭据只交给网关，不能打进运行镜像或放到前端。

查询 `GET /api/agents/substrate/capabilities`，核对环境是否启用 Runner、网关及实例身份。界面显示某项功能，不等于它在当前环境可用。

从 EAP 登记一个独立样例 Agent，激活并声明能力，再通过部署页创建配置式 Runner。保存平台返回的部署请求编号；超时后查询原请求的状态，避免重新创建。

部署完成后还应检查：

- 实际实例和冻结镜像版本一致。
- 实例连接处于已验证状态，任务身份有效。
- 模型名称与网关上游匹配，预算足够但有明确上限。
- 工具仅按任务需要开启，出站范围与数据范围已限定。

首次控制台安装不包含这些配置。目前完整运行系统的接入仍属于有实施支持的过程。

## 4. 创建“计算 → 核验”团队

创建两个独立 Agent，分别负责计算与核验，为每个 Agent 设置一次模型调用额度和明确的输出 Token 上限。不要复用历史演示任务。

创建 Team、加入成员，创建两个顺序步骤的 Plan。两个步骤均使用 `RUNTIME`，声明所需能力并分配相应成员。

计算步骤要求输出 `{"sum":3}`，可配置以下结构契约：

```json
{
  "version": "EAP_JSON_V1",
  "source": "JSON_TEXT",
  "schema": {
    "type": "object",
    "properties": {"sum": {"type": "number"}},
    "required": ["sum"],
    "additionalProperties": false
  }
}
```

核验步骤读取 `eapPreviousResults` 中已通过校验的上一结果，输出 `{"verified":true}` 或 `{"verified":false}`。将契约字段改为 `verified`、类型改为 `boolean`。

该契约仅保证形状和类型。`{"sum":4}` 同样满足上述结构，必须由核验步骤或业务验收判断值是否正确。

提交前检查计划、输入、预算和自动挂起选项。已有 UNKNOWN 占用可能阻止自动回收并使后续步骤停止；保留原状态，核对实例后通过 EAP 显式处置。需要由操作者收尾的新计划可关闭自动挂起，但必须在任务结束后确认并挂起本次实例。

提交一次后保存原执行编号。EAP 将冻结执行配置与交接关系，先校验上一输出，再允许下一步使用它。

## 5. 验收结果与异常

从任务目录进入原执行详情，同时检查：

| 检查项 | 需要的证据 |
| --- | --- |
| 流程状态 | 原执行与各步骤有明确终态 |
| 结构验收 | 结果契约通过，或者明确说明未配置 / 未执行验收 |
| 业务结果 | 合成样例为 `sum = 3` 且 `verified = true` |
| 费用 | 模型调用与预算预占、结算归属一致 |
| 观测 | 任务、实例、Agent 与模型 / 工具调用可关联 |
| 资源 | 按计划挂起或释放本次实例；按需要撤销连接 |

`FAILED`、`BLOCKED`、`WAITING_APPROVAL` 与 `EXECUTION_UNKNOWN` 含义不同。尤其是 UNKNOWN：可能已经产生外部调用或费用，不能因为没有可用结果就当成未执行。先查原回执、原预算与原外部效果；只有工具合同支持的操作才可以继续处置。

## 6. 扩展到 MCP 和框架适配

- Kagent 选择的是已实现的 ADK 适配范围，不能据此假设完整 Kagent 控制器、子智能体和 MCP 执行都已接入。
- MCP 发现、观测和执行授权是不同环节。服务元数据进入目录不代表运行程序可以执行其命令。
- stdio / HTTP 观测需要可信宿主配置。eBPF 可以补充主机连接证据，语义级工具追踪仍依赖协议或应用层证据。
- 客户业务工具需逐项定义输入、权限、幂等、效果查询、失败与取消合同，再做隔离验收。

生产前的容量、项目隔离、身份 HA / TLS、整体灾备与长稳测试见[验证边界](VALIDATION.md)。
