# T8-B：治理审批依据

状态：2026-10-15 已部署并完成有界验收。[验收索引](evidence/eap-approval-context-20261015-index.html)、[最终回执](evidence/eap-approval-context-20261015-final.json)。

人工审批必须绑定预检时的策略依据。策略发生变化后，保留历史批准事实，但该批准不能继续授权模型调用；使用新的决策标识重新预检、再审批。

预检冻结全部已启用策略的规范化摘要，内容包括策略 ID、版本、名称、类型、作用域、规则、执行方式，以及 enforcement/fail-closed 配置。摘要覆盖当时未命中的策略，因此新增或启用策略也会使旧审批失效。采用全局保守规则：即使变化暂时不影响该请求，也要求重新预检。停用策略的编辑不影响当前摘要；启用后会影响。规则 JSON 的对象键顺序和空白不产生无意义变化。策略回退产生新版本，不恢复旧审批。

接口增加 `approvalContextState`：

| 值 | 含义 | 批准／复用 |
| --- | --- | --- |
| `CURRENT` | 待审批或已批准，摘要与当前配置一致 | 仍须满足原请求指纹、归属、供应商和模型约束 |
| `CHANGED` | 当前配置已不同 | 拒绝，重新预检 |
| `UNRECORDED` | 旧记录没有可用摘要 | 拒绝，重新预检 |
| `NOT_APPLICABLE` | 非待审批／已批准状态 | 不作为审批凭据 |

`approvalStatus`、`requestAllowed` 和原命中策略继续表达历史决策，不能单独作为当前调用许可。V83 只新增摘要与并发版本字段，旧摘要保留 NULL，不为旧审批补造依据。审批和复用遇到不一致返回 409；失效的待审批仍可拒绝。同一决策键的预检重放不会刷新审批依据。

摘要字段采用 `CHAR(64)`，实体显式指定相同的 JDBC 类型。首次远程发布发现默认字符串映射按 `VARCHAR` 校验而启动失败，已保留失败证据并撤回镜像。隔离 MySQL 审批回归现启用 `ddl-auto=validate`，覆盖与部署环境相同的实体／迁移一致性检查；已执行的 V83 迁移不重写。

复用入口使用独立 READ COMMITTED 事务读取已提交策略，避免外层 REPEATABLE READ 旧快照掩盖变更。决定表的乐观锁保证并发批准／拒绝只有一个最终结果，其审计与状态在同一事务提交。普通和流式网关都会检查审批依据。检查是调用准入边界；在检查后发生的策略变化不取消已经派发的请求。配置开关按当前值比较，没有单独的持久化变更序号。

界面按 `/api/platform/me` 的 `governance` 能力控制预检和审批操作。JWT 控制台请求由后端同一个 `PlatformPermission.GOVERNANCE` 判定；具备能力的账号无需机器凭证，审批人从认证身份取得，不采信请求正文中的审批人。没有治理能力的已登录账号不能通过附加机器凭证绕过检查。无 JWT 的机器预检继续校验原上报凭证，机器凭证不能绕过 JWT 模式下审批接口的登录授权。

依据不一致、未记录或提交中时不能批准；响应未确认时保留原记录并提示刷新核对，不自动重发。账号、权限或组件生命周期变化后，迟到的提交响应不能触发成功提示或刷新。表格明确把历史允许/停止标为“原请求结论”，与当前审批依据分开显示。

验证范围包括策略编辑、启停、新增、回退、无效旧审批、原键重放、旧事务快照、并发批准／拒绝、普通与流式请求不触达上游，以及前端权限和迟到响应。全部应用测试与浏览器执行只在 PoC 集群；隔离测试不等同于真实供应商调用验证。本阶段不请求新的付费模型调用。
